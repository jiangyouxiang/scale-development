# 多智能体题目生成架构

本 Skill 的**题目生成层**用多个 LLM agent 各自扮演不同角色协同工作，
替代 AIGENIE 原有的单模型自适应循环。**心理测量验证层**仍用 `GENIE()` 保留
UVA/EGA/bootEGA 算法。

```
┌─────────────────────────────────────────────────────┐
│               多 LLM 智能体生成层                      │
│   （Codex 编排；先让用户选择真多智能体/显式兜底/仅验证）      │
│                                                     │
│   策略师(Strategist) → 出题者(Writer) → 审查者(Reviewer)│
│       ↕                   ↕                ↕          │
│    用户确认           题项池          审查报告          │
│                                                     │
│   整合者(Integrator) — 会话日志 + 最终题项 CSV         │
└──────────────────────┬──────────────────────────────┘
                       │ items.csv (type, attribute, statement, ID)
                       ▼
┌─────────────────────────────────────────────────────┐
│               AIGENIE 心理测量验证层                    │
│   GENIE(items=read.csv(...), embedding.model=...)     │
│                                                     │
│   嵌入 → 稀疏化 → UVA → EGA → bootEGA → 最终量表      │
└─────────────────────────────────────────────────────┘
```

---

## 一、为什么需要多智能体

AIGENIE 原版的 `generate_items_via_llm()` 用**单一角色**（"expert measurement methodologist"）、
**同一模型**、**相同温度**反复调用 LLM 直到凑够题量。这带来几个问题：

| 问题 | 后果 |
|------|------|
| 单一角色视角 | 所有题项出自同一「人格」，缺乏多样性 |
| 无审查机制 | 题目质量全靠 LLM 一次生成，无二次校验 |
| 无策略规划 | 每个维度的属性分布由 LLM 自由发挥，缺乏系统性 |
| 无过程记录 | 只有最终题项，无法追溯设计意图 |

多智能体架构让每个角色专注于自己的专长，通过**可见的交流过程**（每阶段产出文档）
提升题项的系统性和可追溯性。

## 二、角色定义

### 角色一览

| 角色 | 职责 | 输入 | 输出 |
|------|------|------|------|
| **架构师**（主 Codex） | 编排整个流程、先触发生成模式决策门、按用户选择调用子代理或显式角色模拟、与用户交互 | 构念 JSON | 各阶段调用 + 用户确认 + 模式记录 |
| **策略师** (Strategist) | 制定每维度的题项规划 | 构念 JSON | 生成计划 |
| **出题者** (Writer) | 按策略生成题项 | 生成计划 | 题项 JSON |
| **审查者** (Reviewer) | 检查完整题池、提出修订要求并复核一轮优化 | 题项 JSON / 修订题项 | 第一轮审查报告 + 优化复核报告 |
| **整合者** (Integrator) | 汇总会话过程、核对数量不变量并整理完整输出 | 全部产物 | 会话日志 + 完整题池 CSV |

### 架构师（主 Codex，不可配置）

架构师是 Skill 的执行主体，负责：
1. 先用弹出选择题确认生成模式；用户选择真多智能体时，调用 `Agent`/子代理能力派生策略师→出题者→审查者→整合者
2. 用户明确选择单智能体角色模拟时，才按四角色顺序在同一代理内执行；选择原因必须写入 `generation_session_log.md`
3. 在每个角色产出的节点**暂停并展示给用户**
4. 收集各角色输出并写入 `generation_session_log.md`，其中必须包含 `generation_mode`、`subagents_used`、`mode_decision_source`、`fallback_reason`；若用户明确要求反向题，也记录 `reverse_items` 与风险提示
5. 策略阶段：⛔ 用户确认生成计划后再进入出题
6. 审查阶段：固定执行一轮“审查 → 出题者优化 → 审查者复核”；完成后展示完整题池确认，不把审查建议直接转成删题

### 策略师 (Strategist)

**角色设定**：
> 你是一位经验丰富的心理测量学家和量表设计专家。你的任务是为给定构念的每个维度
> 制定详细的题项生成策略——不是写题目，而是设计题目应该怎么写。

**任务**：
- 阅读构念 JSON（维度名、定义、属性、参考题项、目标人群、语言）
- 对**每个维度**制定：
  - 该维度的题项侧重（每个属性下应有哪几类题目）
  - 题项方向（默认全正向；不主动询问反向题。仅当用户明确要求反向题时，才安排正反比并标注高风险）
  - 难度/极端性分布（覆盖面）
  - 避免与相邻属性内容重叠的边界标记
- 输出 **《题项生成计划》**（结构化文本）

**注意事项**：
- 不写具体题目，只写「题目应该怎么写」
- 计划中标注中文规范约束（如适用）
- 对于不熟悉的构念面，标注需要用户补充的方向

### 出题者 (Writer)

**角色设定**：
> 你是一位熟练的测量题目写手，擅长将构念定义转化为简洁、清晰、心理测量学上
> 有效的量表题项。你严格遵循给定的生成策略。

**任务**：
- 按策略师的计划，为每个维度下的每个属性生成题项
- 输出格式：严格按 `JSON 数组`
  ```json
  [
    {"type": "维度名", "attribute": "属性名", "statement": "题项文本"},
    ...
  ]
  ```
- 每批生成后自行去重（同批内语义查重）
- 遵循中文/英文编写规范

**注意事项**：
- 严格遵循策略师的计划，不偏离
- 不生成策略师未规划的题项
- 每条题项独立、不重复、不近义
- 如一个维度有多个属性，轮替生成（不要集中写完一个属性再写下一个）

### 审查者 (Reviewer)

**角色设定**：
> 你是一位严格的量表质量审查员。你的工作是发现题项的问题，而不是夸奖。
> 你对内容效度、语句质量、维度归属有近乎苛刻的标准。

> ⚠️ **审查者 ≠ 专家内容效度证据**：审查者是 LLM 评 LLM 生成的题，且常与出题者同属一个
> 模型谱系，独立性有限、可能共享盲点。原论文（§9）明确把"用 LLM 评价 LLM"列为危险信号。
> 因此审查者的"内容效度"判断只是**生成内部的一道自检**，**不能等同于外部 SME 专家组的
> CVI / CVR / Aiken's V**。正式效度仍需独立领域专家评定。见 `reference/methodological-boundaries.md` 第六节。

**审查维度**：

| 维度 | 具体内容 |
|------|----------|
| 内容效度 | 题项是否确实测量了该属性？是否有跨维漂移？ |
| 语句质量 | 语法是否正确、有无歧义、是否自然（中文：有无翻译腔） |
| 区分度 | 同属性题项之间是否有足够语义差异？ |
| 规范遵从 | 是否符合策略师计划？默认是否全正向？若用户明确要求反向题，是否已记录高风险并按设置执行？是否遵守中文编写规则？ |
| 表面效度 | 题项是否明显测量了它声称要测量的内容？ |

**输出**：结构化第一轮审查报告
- **通过**：题项可直接保留
- **需要改写**：标记题项 ID + 问题描述 + 可执行改写要求
- **需要替代**：标记题项 ID + 问题描述 + 同维度/同属性替代要求；不得由审查者直接删除
- **总体评价**：通过率、主要问题类型、各维度风险

审查报告完成后，必须交给出题者执行且仅执行一轮内容优化。优化后由审查者输出复核报告，确认改写/替代题、残留风险和数量配额。生成层的优化不减少题项总数；若原题无法修复，必须由出题者生成同维度、同属性替代题。

### 整合者 (Integrator)

**角色设定**：
> 你是一位技术文档工程师，负责将多智能体生成的全过程整理为结构化的
> 生成会话日志和标准的题项数据文件。

**任务**：
1. 整理**生成会话日志** `generation_session_log.md`：
   - 构念基本信息
   - 策略师计划摘要
   - 出题者产出概览（各维度题数）
   - 审查者结论（通过率、主要问题）
   - 如有修订，记录修订轮次与改动概要
2. 输出**题项 CSV** `generated_items.csv`（4 列）：
   - `type` — 维度名
   - `attribute` — 属性名
   - `statement` — 题项文本
   - `ID` — 唯一编号（从 1 开始连续）
3. 与架构师核对确保所有题项信息完整
4. 核对优化前后总题数、各维度题数、属性配额和 ID 连续性；任何不一致都必须返回出题者修复，不得静默删题
5. 确认 `generated_items.csv` 是完整候选题池；`genie_final_items.csv` 只能由 GENIE/local_GENIE 生成，不能作为输入


## 二点五、生成模式决策门

在策略师开始前必须暂停，并优先通过 Codex 弹出选择题让用户选择生成模式；没有用户明确选择前，不得进入策略师阶段：

| 选项 | 名称 | 何时使用 | 约束 |
|------|------|----------|------|
| A | 真多智能体协同（推荐） | 需要体现本 Skill 核心、多角色并行或交叉审查 | 使用子代理/多代理；每个角色产物独立记录 |
| B | 单智能体角色模拟（显式兜底） | 用户追求速度，或当前环境没有子代理能力 | 必须由用户明确选择；不可自动降级 |
| C | 已有题池仅验证 | 用户已有完整候选题项，只需要 GENIE 语义筛查 | 跳过生成层，直接把用户确认的完整题池交给 provider 决策；GENIE 内部才执行削减 |

执行规则：

- 默认推荐 A，但**不得自动执行 A 或 B**；必须等待用户点击选择，不能因用户说“继续”而跳过。
- 如果用户选 A 而工具不可用，不能静默改成 B；应再次弹出选择题请求用户决定。
- `generation_session_log.md` 的开头必须记录：`generation_mode`、`subagents_used`、`mode_decision_source`、`fallback_reason`；若用户明确要求反向题，还要记录风险提示已给出。
- B 模式下仍要保留四个角色的独立小节，避免退化为普通“一次性生成”。

## 三、交互流程（完整）

```
架构师 → 策略师
    ↓
策略师 → 《题项生成计划》
    ↓
⛔ 用户：确认/修改计划
    ↓
架构师 → 出题者（每个维度可并行）
    ↓
出题者 → 题项 JSON（每维合并）
    ↓
架构师 → 审查者
    ↓
审查者 → 《第一轮审查报告》
    ↓
出题者：固定执行一轮优化（改写/同维度同属性替代）
    ↓
审查者 → 《优化复核报告》
    ↓
整合者：核对数量不变量并输出完整题池
    ↓
⛔ 用户：确认完整候选题池后进入验证
```

## 四、关键原则

### 角色隔离
- 每个 agent **只做自己被设定的任务**，不做其他角色的事
- 策略师不得写题，出题者不得做第一轮审查或复核，审查者不得直接改写题面；但审查报告交付后，**Writer 必须负责固定一轮优化**，这是 Writer 的后续职责，不新增第五个智能体

### 过程可见
- 每个角色的输出都是**独立的可读文档**
- 架构师在每个节点暂停，展示给用户
- 最终 `generation_session_log.md` 保留完整的决策链

### 人类在环
- 策略计划 → 用户确认后执行
- 第一轮审查报告 → Writer 固定优化一轮 → Reviewer 复核；不得再询问是否修订，也不得因审查建议直接删题
- 最终题项 → 用户确认后进入心理测量验证

### 中文适配
- 中文量表中，策略师、出题者、审查者、整合者**全部用中文交流**
- 策略计划 / 审查报告 / 会话日志 → 中文
- 题项 JSON → `statement` 值为中文，`attribute` 和 `type` 仍用构念中的值（可中文）

## 四点五、生成层的数量不变量与验证边界

- 出题者第一轮生成多少题，优化后仍必须输出多少题。
- 每个维度和属性的题量配额必须保持不变；题量以用户确认的完整候选题池和策略师配额为准。
- 审查者可以指出“不适合原样保留”，但不得直接删除；出题者必须改写或生成同维度、同属性替代题。
- `generated_items.csv` 是完整候选题池，是唯一的 GENIE/local_GENIE 输入。
- `genie_final_items.csv` 是验证层输出。若从 N 题保留 K 题，K 题代表语义筛查后的结果，而不是验证前的简版输入。

## 五、输出文件格式

### generated_items.csv

```csv
type,attribute,statement,ID
<dimension>,<attribute>,<statement>,1
<dimension>,<attribute>,<statement>,2
<dimension>,<attribute>,<statement>,<optional_difficulty_or_batch>
...
```

### generation_session_log.md

```markdown
# 题项生成会话日志

## 生成模式
- generation_mode: 真多智能体协同 / 单智能体角色模拟 / 已有题池仅验证
- user_choice: [记录用户选择]
- subagents_used: true/false
- fallback_reason: [如适用]

## 构念信息
**构念名**：<construct_name>
**语言**：<language>
**目标人群**：<target_population>

## 策略摘要
- <dimension_A>（<m> 个属性）：说明该维度的测量边界、题项侧重与排除内容
- <dimension_B>（<n> 个属性）：说明该维度的测量边界、题项侧重与排除内容

## 出题概况
| 维度 | 属性数 | 生成题数 | 目标题数 |
|------|--------|---------|---------|
| <dimension_A> | <m> | <target_items_A> | <target_items_A> |
| <dimension_B> | <n> | <target_items_B> | <target_items_B> |

## 审查结论
- 通过率：96.7%（116/120）
- 修订 4 题（含 2 题跨维漂移、2 题语句歧义）
- 删除 0 题
- reverse_items：默认不含；若用户明确要求反向题，记录比例与风险提示

## 角色模型记录（按实际 Codex 环境填写）
| 角色 | 模型 |
|------|------|
| 策略师 | Codex 可用高能力模型 |
| 出题者 | Codex 可用高效率模型 |
| 审查者 | Codex 可用高能力模型 |
| 整合者 | Codex 可用高效率模型 |
```
